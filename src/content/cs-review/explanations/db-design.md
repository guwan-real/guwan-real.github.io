## 数据库设计先问业务事实，而不是先建表

图书馆说“我们需要一个借书系统”，这还不足以决定表结构。必须追问：记录的是一本书的书目信息，还是书架上某一本实体副本？一本书有多本副本时怎么编号？是否保留已经归还的历史？一位读者是否可以反复借同一本副本？

不同答案会产生不同结构。若没有区分书目与副本，就可能用一个“数据库原理”记录代表所有实体书，最后无法回答哪一本已借出、哪一本损坏。**表结构是在表达业务事实，不只是为界面准备字段。**

本章用一个自编借阅系统，从需求走到约束和访问路径。数据库设计与软件开发相互配合，但数据库有自己的概念、逻辑、物理设计职责。

## 设计各阶段分别产出什么

| 阶段 | 主要任务 | 借阅例子的产出 |
| --- | --- | --- |
| 需求分析 | 说明要保存的事实、规则、操作与规模 | 保留借还历史，同一副本同时最多一条未归还记录 |
| 概念设计 | 用业务对象及联系表达需求 | 读者、书目、副本、借阅及其联系 |
| 逻辑设计 | 转为关系、键、约束并规范化 | Reader、Book、Copy、Loan 表 |
| 物理设计 | 根据访问方式安排存储和索引 | 按读者与借出时间查询的联合索引 |
| 实施与测试 | 建表、导入、开发事务并验证 | 建库脚本、并发借书测试、数据迁移 |
| 运行维护 | 监控、备份、调优及演进 | 恢复演练、慢查询分析、容量管理 |

这些阶段可以迭代。发现一条关键查询缺少需要的属性，可能回到需求和逻辑设计补充，而不是只在物理层不断加索引。[作者 E-R 课件](https://www.db-book.com/slides-dir/PDF-dir/ch6.pdf)给出了从需求到概念、逻辑和物理设计的区分。

## E-R 中的实体、属性与联系

实体是能够与其他对象区分的业务对象，如读者 R01、某本具体副本 P101；实体集是同类实体的集合。属性描述实体，如读者姓名、副本条码。联系描述对象之间的关联，如某读者借阅某副本。

不要只按“名词一定是实体、动词一定是联系”机械划分。借阅本身有发生时间、到期时间、归还时间，需要保留历史，也可以作为有独立标识的业务实体来设计。

本章规定：一份 Loan 代表一次借阅事件；每次事件恰好关联一位读者与一本副本；一份书目可以有多本副本；副本只能属于一份书目。

## 联系基数与参与约束要分别说清

1:1、1:N、M:N 常用于描述最大关联数量；“能否为零”是另一层约束。

- 一位读者可以有 0～N 次历史借阅；每次借阅必须关联 1 位读者。
- 一本副本可以有 0～N 次历史借阅；每次借阅必须关联 1 本副本。
- 一份书目可以有 0～N 本副本；每本副本必须关联 1 份书目。

“副本同时只能借给一个人”限制的是**尚未归还的借阅集合**，不表示它一生只能有一条 Loan。若把 Copy 与 Loan 永久设计成 1:1，会无法保存第二次借阅历史。

同样，“每个借阅必须有读者”是 Loan 对 Reader 的必须参与；“每位读者必须借过书”则是另一个规则，本例不成立。最大基数和最小参与数量要分别从业务中提取。[Berkeley E-R 讲义](https://cs186berkeley.net/notes/note13/)可对照学习这两类约束。

## 从 E-R 到关系表的基本映射

**1:N 联系**通常把“一方”的键放在“多方”作为外键。Book—Copy 是 1:N，于是 Copy 有 book_id。不能给 Copy.book_id 加 UNIQUE，否则同一书目最多只剩一本副本，误变成 1:1。

**M:N 联系**通常单独建联系表。例如学生—课程用 Enrollment(sid,cid,score)。两个外键合起来可以作为候选键，联系本身的成绩放在选课表，而不是学生或课程表中。若同一学生可以跨学期重复修同一课程，键还需要加入学期或使用能区分修读事件的标识。

**1:1 联系**可以在适合的一方放外键并加 UNIQUE。例如单独保存读者扩展资料 `ReaderProfile(reader_id UNIQUE, ...)`，每位读者最多一份资料。是否 NOT NULL、是否与主表合并，要看必须参与、可选属性和生命周期，不能仅由 1:1 三个字符决定。

**弱实体或局部编号**要连同所属对象一起识别。例如 Copy 只使用“同书目内的副本号 copy_no”，则 `(book_id,copy_no)` 可联合标识副本；copy_no=1 在不同书目下重复是正常的。也可以使用全局唯一 copy_id，并对 `(book_id,copy_no)` 增加业务唯一约束。

**自联系**也能映射成表内外键。例如 Employee.manager_id 引用 Employee.emp_id，表示员工的上级；顶层负责人可为空。外键本身不自动排除管理链条出现环，若业务禁止环，还需另行约束。

三元联系不能总是随意拆成三个二元联系。例如“某供应商向某项目供应某零件”，只保留供应商—项目、供应商—零件、项目—零件，可能拼出原本没有发生的三元组合。映射前必须保留完整语义。

## 把核心事实放进一组关系

本章可采用：

```text
Reader(reader_id, name, phone)
Book(book_id, title)
Copy(copy_id, book_id, barcode)
Loan(loan_id, reader_id, copy_id, borrowed_at, due_at, returned_at)
```

reader_id、book_id、copy_id、loan_id 分别为主键；barcode 为业务唯一值；Copy.book_id、Loan.reader_id、Loan.copy_id 为外键。归还时间允许 NULL，用于表示尚未归还。

为何不把书名和读者电话复制到每条 Loan？这些值描述的是书目或读者，直接重复保存会增加更新成本。若业务要求保留“借阅发生时的联系信息快照”，则这是新的历史事实，可以有意识地单独建模，不能把所有重复都一概删除。

使用代理主键也不表示业务约束消失。例如 loan_id 唯一，仍不能阻止同一本副本存在两条同时未归还的记录；barcode 仍需业务唯一约束。**主键解决记录标识，不包办所有业务正确性。**

## 约束与事务：让并发请求也遵守规则

Loan 的简化定义可以是：

```sql
CREATE TABLE Loan (
  loan_id VARCHAR(20) PRIMARY KEY,
  reader_id VARCHAR(20) NOT NULL REFERENCES Reader(reader_id),
  copy_id VARCHAR(20) NOT NULL REFERENCES Copy(copy_id),
  borrowed_at TIMESTAMP NOT NULL,
  due_at TIMESTAMP NOT NULL,
  returned_at TIMESTAMP,
  CHECK (due_at > borrowed_at),
  CHECK (returned_at IS NULL OR returned_at >= borrowed_at)
);
```

这保护了标识、引用和单行时间规则，但没有表达“同一副本最多一条未归还”。在 PostgreSQL 中，可以用部分唯一索引表达这条特定规则：

```sql
CREATE UNIQUE INDEX one_open_loan_per_copy
ON Loan(copy_id)
WHERE returned_at IS NULL;
```

它只对未归还记录要求 copy_id 唯一，历史归还记录不受这个唯一性限制。这是产品相关做法，其他 DBMS 可能需要不同表达；不能当成所有数据库通用语法。[官方部分索引文档](https://www.postgresql.org/docs/18/indexes-partial.html)解释了只为满足谓词的行建立索引的思路。

为什么仅在应用中“先查没有借出，再插入”不够？两个请求可能都先查到没有，然后各自插入。因此要让约束或合适的锁和隔离机制参与协调。借书流程可以在一个事务中锁定对应 Copy 记录，校验状态，再插入 Loan；并发冲突时处理失败或重试。

若还要求“每个读者最多借 5 本”，这是跨多行规则；只锁一本副本不一定够，还要协调同一读者的并发借阅。事务边界应围绕业务不变量划定，而不是简单地每条 SQL 单独提交。

## 用业务反例审查结构，常比只看字段清单有效

设计完成后，可以尝试构造四种反例。第一种是同一副本同一时刻被两人借出，看是否有数据库约束或事务协调阻止；第二种是新读者尚未借书，看系统能否独立保存读者；第三种是删除最后一条借阅，看书目和副本是否仍然存在；第四种是归还历史后再次借阅，看键与唯一约束是否错误阻止了它。

这些反例分别检查并发不变量、插入独立性、删除影响与历史表达能力。没有异常提示不等于设计合理：如果应用根本无法表达“还没有副本的书目”，问题发生在模型，而不是某次输入验证。

还可以列出访问矩阵：登记读者会写 Reader；查询某读者最近记录会读 Loan 并连接 Copy、Book；借书会读取读者和副本、写 Loan；归还会更新一条尚未归还的 Loan。由此反推必要字段、关联路径、事务边界和权限，避免只建一组“看起来完整”的表，却无法支持核心操作。

数据类型同样服务语义。用日期表示生日、用时间戳表示一次借出事件；金额或需要精确十进制的业务值应考虑相应精确类型；标识中的前导零若有意义，就不应随便转成普通整数。选类型不是为了看起来节省几个字符，而是让合法值、比较与运算符合实际含义。

## 索引从常用查询出发

假设最常见查询是“读者 R01 最近的 20 次借阅”：

```sql
SELECT loan_id, copy_id, borrowed_at
FROM Loan
WHERE reader_id = 'R01'
ORDER BY borrowed_at DESC
FETCH FIRST 20 ROWS ONLY;
```

可以考虑 `(reader_id, borrowed_at)` 联合索引，因为先固定读者，再按时间取少量记录。联合 B 树索引的列顺序会影响能缩小的扫描范围，但不能死记“没用第一列就绝对不能使用索引”，实际优化器和索引机制还可能采用其他策略。[官方多列索引文档](https://www.postgresql.org/docs/18/indexes-multicolumn.html)给出了更具体的规则。

索引不是越多越好：INSERT、UPDATE、DELETE 也要维护相关索引，索引还占空间。低选择性条件、小表、一次要读大半张表时，扫描可能合理。应从查询条件、排序、连接列、数据量和写入频率作判断。

`EXPLAIN` 展示计划，`EXPLAIN ANALYZE` 还会实际执行并提供测量信息。检查估算行数是否偏离实际、连接是否放大结果、是否有大量排序或读页，比只问“有没有走索引”更有意义。[官方 EXPLAIN 文档](https://www.postgresql.org/docs/18/using-explain.html)可作为后续实践入口。

## 应用开发还要避免什么

N+1 查询指先查 N 条主记录，再为每条记录各发一次关联查询，总共约 1+N 次请求。例如查 20 条 Loan 后逐条查 Copy、Book，会产生很多往返。可以按业务改成连接查询或批量查询，但必须留意分页和一对多连接导致的重复行。

测试也要覆盖“没有记录、重复记录、边界时间和同时请求”。只测“单个人顺利借一本书”无法发现并发双借问题。对输入值使用参数化查询；前端校验提升体验，数据库约束提供共享的数据底线，两者各有作用。

结构演进时，新增必填字段通常涉及旧数据如何补齐、旧版应用还能否工作、何时加约束等问题。可采用先兼容新增、回填核查、再收紧约束的分步方式。备份、迁移验证和回退方案属于实施与运维，不应在建表之后被遗忘。

## 设计题的作答方法与自查

建议按“事实 → 数量约束 → 表 → 键 → 业务约束 → 事务 → 访问路径”写答案。每增加一个约束，说明它防止什么反例；每增加一个索引，说明它服务哪类查询。

自查：

1. 书目与副本为何分表？**一本书目信息可以对应多个独立可借还的实体副本。**
2. Copy.book_id 加 UNIQUE 会怎样？**在该建模下，把一本书目可有多本副本限制成最多一本。**
3. loan_id 唯一是否足以防止一份副本同时借给两人？**不足，还需对未归还记录作相应约束和协调。**
4. 多建十个索引就一定更快吗？**不一定，必须结合查询收益与写入、存储成本。**
