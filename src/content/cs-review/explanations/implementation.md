## 系统开发把设计变成能重复运行的成果

报修系统已经规定“学生只能撤销本人未接单的工单”，设计也明确了接口和状态。现在需要把这些约定落实到程序、配置和构建过程。**编码**是编写程序语句；**系统开发或实现**还包含模块协作、接口实现、代码检查、版本记录、依赖管理和构建等活动。

可以把源代码比作制作说明，构建产物比作按说明制作出的成品。别人电脑上“同样的代码”运行失败，原因可能是依赖版本、编译选项、数据库结构或配置不同。因此，实现的目标不仅是“我这里能运行”，还要让团队知道运行的是哪一版、用什么条件产生、怎样检查它。

## 语言与执行：不要把语言名称当成绝对分类

**程序设计语言**提供表达数据和操作的规则。机器执行时，通常要经过编译、解释或两者结合。编译把一种程序形式转换为另一种形式；解释按某种表示执行程序；有的运行环境会先生成中间代码，再在运行中编译热点部分。具体方式由语言实现与运行环境决定，不能只凭语言名字断言“永远纯编译”或“永远纯解释”。

静态类型检查通常在运行前检查某些类型约束，动态类型检查通常在运行时发生。它们不等于“强类型与弱类型”的简单同义词，也不决定程序是否必然可靠。类型检查能发现把文本误当整数的一类问题，却不能自动发现“错误地允许学生撤销他人工单”这样的业务错误。

选择语言时应结合现有系统、团队能力、依赖、运行环境、性能和维护成本。给一个简单校内工具选最复杂的新技术，未必能改善结果；因为熟悉某语言而忽视硬件与实时约束，也不是完整的工程判断。

## 编程范式：同一问题可以从不同角度组织

**范式**是组织程序与思考计算的方式，很多语言支持不止一种。下面用“找出待接单工单”说明它们在关注什么。

**过程式**把工作拆成按步骤执行的过程：读出记录，循环判断状态，把符合条件的记录放入结果。它直观表达控制流程，适合理解算法，但如果所有代码共享大量可变数据，修改时容易产生相互影响。

**面向对象**把相关数据与行为组织到对象中。例如工单对象维护状态，提供 `cancelBy(student)` 操作，由操作统一检查归属和状态。封装能帮助保持业务规则，但“把函数全塞进一个巨大类”不会自动得到良好设计，继承层次也不是越深越好。

**函数式**重视函数组合、明确输入输出与减少不受控的状态变化。例如从工单集合筛选待接单项，得到新集合而不修改原集合。**纯函数**在相同输入下返回相同结果，并且没有可观察的外部副作用，因此往往容易单独测试。发送短信、写数据库本来就涉及副作用，可以把这些操作与纯计算部分分开。

**声明式**更强调说明想要什么结果，减少显式说明每个执行步骤。SQL 中写 `WHERE status = '待接单'` 表达筛选条件，具体访问路径由数据库选择。函数式与声明式也有交集，范式不是彼此完全封闭的盒子。

## 完整例子：撤销工单为什么不能只改一个字段

先把规格写在实现前：请求者必须已登录，必须是工单所有者，工单必须待接单；成功后保留记录并变为已撤销。教学用伪代码如下：

```text
cancelOrder(currentUser, orderId):
    requireAuthenticated(currentUser)
    order = repository.find(orderId)
    if order 不存在: 返回约定的失败结果
    if order.ownerId != currentUser.id: 拒绝访问
    if order.status != "待接单": 拒绝撤销
    尝试以“当前仍为待接单”为条件更新状态为“已撤销”
    if 没有更新记录: 返回状态已变化
    记录必要审计信息
    返回成功
```

逐步看每个判断的目的。身份检查确定“你是谁”；归属检查确定“你能否操作这个对象”；状态检查确定“业务此时是否允许”。请求参数中的 `studentId` 不能替代已经认证的身份，否则攻击者可改成别人的编号。

最后还要考虑并发：学生检查到待接单后，维修员可能刚好接单。若先查询、再无条件更新，就可能覆盖新状态。因此实现需把条件与更新保持一致，例如使用符合数据库并发规则的条件更新或事务。需求决定允许何种结果，设计与实现选择怎样保证它。

接口还要约定重复调用行为。网络超时后学生重试，如果原操作已经成功，应得到合理结果，而不是产生混乱。不能只看一次正常调用“输出成功”就断定实现完整。

## 可读、可查、可维护：编码规范与错误处理

命名应表达业务含义，例如 `canCancel` 比 `flag2` 清楚；一个函数应围绕明确职责组织，避免把权限、界面拼接、数据库连接和短信发送混成难以检查的一团。注释适合说明为什么采取某种不直观做法，而不是把每行代码逐字翻译一次。

**异常或错误处理**要区分可预期的业务拒绝与意外故障。已接单不能撤销，是业务规则；数据库无法连接，是运行故障。前者应返回可理解的业务结果，后者需要记录诊断信息并按约定处理。把所有错误都吞掉并返回成功，会让用户和监控同时失去真实情况。

**日志**记录关键事件以便定位问题。通常应包含时间、请求或关联标识、操作和结果等必要信息。若一张工单跨多个模块处理，相同关联标识可以串起过程。日志不应为了方便而无差别打印密码、令牌或完整敏感数据；“日志越多越好”同样忽视了可用性、成本和信息保护。

代码审查是人检查修改的目的、正确性、边界、可维护性和相关测试。静态检查工具可以发现某些类型错误、未使用变量或危险模式，但工具无法替团队理解全部业务。审查过的代码仍可能有缺陷，工具全绿也仍需合适测试。

## 重构：改变内部结构，保持可观察行为

**重构**通过小步调整改善现有代码内部结构，同时保持可观察行为。它与新增功能、修正业务行为的目标不同。修复错误往往会改变先前错误的输出，不能把这种变化本身称为纯粹重构。

例如撤销、完成和转派三个操作都复制了同一段归属检查。团队先用测试记录目前应保留的成功与拒绝行为，再抽取 `checkOwnership`，逐个替换调用，运行相关测试。结构更清楚，而接口结果、权限规则与外部行为保持不变。

如果抽取时顺便把“管理员也允许撤销”的新规则加进去，就同时发生了需求变更与结构调整。可以分别完成并记录，便于判断失败来自哪种原因。没有测试证据时，大幅改写后声称“我觉得行为一样”，风险明显高于可逐步验证的变换。

## 版本控制：让多人修改有共同历史

版本控制记录文件如何随时间变化，使团队能够比较、追踪和恢复版本。Git 中的一次提交记录一组相关修改；分支允许围绕不同任务组织历史；合并把相关修改整合起来。提交记录不是只给工具看的，清楚说明“为何修改”有助于后来排查。

假设甲修改撤销规则，乙修改工单详情界面。两人在各自分支工作，合并前检查差异与测试。如果两人修改了同一段文本，工具可能提示冲突，需要理解双方意图后决定最终内容，不能机械地“全选我的”或“全选对方的”。

更隐蔽的是**语义冲突**：甲把状态名从“待处理”改为“待接单”，乙在另一文件里新增了仍判断“待处理”的统计。文本可能自动合并成功，程序含义却不一致。因此“合并没有冲突提示”不等于“集成正确”。

已经提交的代码并不等于线上正在运行的版本。团队还要记录软件包、配置和部署环境之间的关系，才能回答“某次故障对应哪一组修改”。误删文件也不能仅依赖版本控制恢复全部业务数据，数据库备份有不同职责。

## 配置管理、构建与依赖：知道到底交付了什么

**软件配置管理**关注受控成果的标识、版本、变更、状态与一致性，范围比代码版本控制更大。需求、设计、源代码、测试、构建脚本、依赖清单和发布配置都可能成为配置项。**基线**是经过认可的某个版本组合，为后续变更提供参照。

“把数据库地址写进配置文件”只是配置的一种使用，不能把配置管理缩成修改几项参数。若程序已换新接口，文档、测试和部署配置仍停在旧版，就没有保持产品与信息的一致。

**构建**把源代码及相关资源转换为可运行或可分发的成果，可能包括生成代码、编译、链接、资源处理与打包，具体步骤依项目而定。**依赖管理**则说明需要哪些外部库及版本。锁定依赖、记录工具链和构建参数，有助于避免今天自动下载到不同版本而改变产物；“可重复”还需要控制时间戳等影响产物的因素。

例如发布记录可以关联：代码提交 `c123`、依赖锁文件、运行环境版本、构建编号、软件包校验值、数据库迁移版本及配置版本。出现问题时，团队才有依据还原或比较，而不只是寻找一个名叫“最终版.zip”的文件。

## 持续集成与系统集成：尽早发现连接处的问题

**集成**把各模块连接为整体，并检查接口及协作。单个模块通过测试，仍可能出现日期格式不同、字段单位不同、超时约定不同等问题。接口契约应明确输入输出、数据类型、错误、权限和兼容性，而不只是一条地址。

**持续集成（CI）**强调频繁整合小步修改，并自动构建和检查，使问题较早暴露。一次典型流程是：提交修改触发构建，检查代码，运行合适的单元与集成测试，保存报告与产物。失败应得到处理，长期忽略的红色检查无法提供有效反馈。

CI 不是必须每次直接上线，也不能保证覆盖未编写的业务场景。持续交付和持续部署解决更后面的发布安排，第 44 章继续说明。

单体系统把主要功能作为一个整体部署，初期可能较容易开发与排查；微服务把能力拆成可独立部署的服务，也引入网络调用、分布式故障、数据一致性和运维成本。对小型报修系统，良好模块化的单体可能足够；“服务越多越先进”不是工程结论。

## 解题方法与自查

看见“记录谁改了什么、比较旧版本”，优先想到版本控制；看见“统一管理代码、文档、配置及基线变更”，想到配置管理；看见“合并后自动构建测试”，想到持续集成；看见“改善结构而不变行为”，想到重构。关键是目的与范围，不能只凭一个工具名称判断。

检查自己能否解释三个现象：自动合并成功却测试失败，可能是语义冲突；同一代码在另一环境失败，需比较依赖与配置；重复请求生成两次业务副作用，需检查接口约定和幂等处理。能从现象追溯具体机制，就比孤立背术语更接近实际开发。

## 补充：顺序、选择、循环可以嵌套组成清楚的控制流程

结构化程序的三种基本控制结构是**顺序、选择、循环**。顺序表示先后执行，选择表示按条件进入分支，循环表示重复执行一段操作。它们描述控制流程，不能与“过程式、面向对象、函数式”这类程序组织范式混为一组。

用一个小例子走一遍：累加列表 `[2,-1,4]` 中的正数。

```python
total = 0
for value in [2, -1, 4]:
    if value > 0:
        total = total + value
print(total)
```

| 读到的 value | value > 0 | 本轮动作 | 本轮后 total |
| --- | --- | --- | --- |
| 2 | 真 | 加上 2 | 2 |
| -1 | 假 | 不执行累加分支 | 2 |
| 4 | 真 | 加上 4 | 6 |

先初始化，再遍历，最后打印，体现顺序；for 重复处理每个值，体现循环；if 决定当前值是否参与，体现选择。**选择可以在循环内，循环也可以在分支内**，不是每个程序只能三选一。[Python 条件与循环参考](https://docs.python.org/3/reference/compound_stmts.html)可用来核对这些语句的执行含义。

做过程跟踪题时，为变量列一张“执行前、条件、本轮后”的表，先按程序走，不要按希望它得到的结果倒推。比如把判断误读成 `value >= -1`，结果会变成 5；把累加误读成 `total = value`，最后虽为 4，却已经换了算法。

GOTO 是显式跳转机制，不是与这三种并列的第四种基本结构。结构化强调控制关系易于理解和检查，也不等于所有实际语言中的 return、break 或异常处理都必须被机械禁止；阅读时仍应按语言规则理解它们怎样改变流程。
