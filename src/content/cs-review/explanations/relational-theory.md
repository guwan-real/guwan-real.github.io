## 关系理论是在解决什么问题

关系数据库不只是“把数据放进格子”。它还要回答：哪几列能认出一条记录？哪些列之间存在必然联系？一张表混进太多种事实，会不会导致重复和矛盾？拆成几张表后，是否还能准确还原原来的信息？

本章先用小表理解术语，再手算闭包与范式。范式的判断依据是**关系模式及其业务约束**，而不是表看起来整不整齐，也不是当前有没有重复行。下面所有业务和数据都是自编教学例子。

## 关系、元组、属性、域分别是什么

设学生关系模式为 `Student(sid, name, dept_id)`：

| sid | name | dept_id |
| --- | --- | --- |
| S01 | 安禾 | D10 |
| S02 | 柏青 | D10 |

一行是一个**元组**，一列的名称是一个**属性**，每个属性允许取值的集合称为**域**。例如 sid 的域可以理解为符合学校编号规则的学号集合。关系模式描述结构；这两行构成一个时刻的关系实例。

属性有 3 个，称关系的度或目为 3；元组有 2 个，称该实例的基数为 2。交换两行的位置不会改变数学意义上的关系。经典关系采用集合语义，同一个元组不重复；SQL 查询默认通常保留重复行，只有需要时才用 `DISTINCT` 去重。不要直接把纯关系代数的结论搬到 SQL 的多重集结果上。

一行里的列之间也没有“第一列天然是主键”的规则。主键是设计者依据约束选定的，不是根据显示位置决定的。

## 从“能唯一认出记录”区分各种键

假设 Student 中的学号 sid 和证件号 card_no 都唯一，姓名允许重名。关系为 `Student(sid, card_no, name)`。

| 名词 | 判断标准 | 本例 |
| --- | --- | --- |
| 超键 | 一组属性能唯一确定一个元组 | `{sid}`、`{sid, name}` 都可以 |
| 候选键 | 超键，而且删掉任一属性后就不再是超键 | `{sid}`、`{card_no}` |
| 主键 | 从候选键中选出的主要标识 | 可以选 `{sid}` |
| 主属性 | 出现在至少一个候选键中的属性 | sid、card_no 都是主属性 |
| 非主属性 | 不属于任何候选键的属性 | name |

“最小超键”的最小指**不能再删属性**，不是要求在所有候选键中属性个数最少。一个模式可能同时有一个单属性候选键和一个复合候选键。也不能把“主属性”误解为“被选作主键的那几个属性”。

选课表中的 sid 可以作为外键，引用 Student 的候选键或符合 DBMS 要求的唯一键。外键值并不要求在本表中唯一，因为一名学生可以有多条选课记录。外键也不天然要求非空；如果业务必须关联学生，应再规定 `NOT NULL`。[PostgreSQL 约束文档](https://www.postgresql.org/docs/18/ddl-constraints.html)可用于核对实际 SQL 中的主键和外键规则。

## 函数依赖：相同的左边，必须有相同的右边

`X → Y` 读作“X 函数决定 Y”。它要求：在每一个合法关系实例里，只要两个元组在 X 上相同，在 Y 上就必须相同。它不是说计算机一定能用某个公式把 Y 算出来。

例如每个学号对应一个姓名，因此 `sid → name`。两名学生可以同名，所以不能反推 `name → sid`。每门课程的名称固定，因此 `cid → course_name`；同一学生可以有多门课程的成绩，因此通常没有 `sid → score`，应是 `(sid, cid) → score`。

只看两行样本很容易误判。如果当前两名学生恰好姓名不同，只能说明样本中没有反例，不能证明姓名永远唯一。函数依赖来自业务语义，或题目明确给定的依赖集合 F。题目若说“依赖仅由 F 推导”，就不要自行添加“姓名不会重复”等假设。

还有两组需要区分的词：

- `XY → Z`，且属性集 XY 的任何真子集都不能决定 Z，称 Z 对 XY 完全函数依赖；若某个真子集（例如 X 单独）已经能决定 Z，则存在部分依赖。
- `X → Y` 且 `Y → Z`，可以推出 `X → Z`，这体现依赖的传递性。判范式时还要检查中间属性是否为键、右部是否为非主属性，不能见到两支箭头就直接判不满足 3NF。

## 属性闭包：把“能推出什么”一步步写出来

属性集 X 在依赖 F 下的闭包记为 `X⁺`，表示从 X 出发，通过 F 能确定的所有属性。计算方法很机械：先放入 X；若某条依赖的左部已经全部在集合中，就加入右部；重复直到集合不再扩大。

设 `R(A, B, C, D)`，依赖为：

```text
A → B
B → A
C → D
```

求 `{A, C}⁺`：

| 轮次 | 已掌握属性 | 这一轮能做什么 |
| --- | --- | --- |
| 初始 | A、C | 只能使用题给的起点 |
| 第 1 轮 | A、B、C、D | A→B 加入 B，C→D 加入 D |
| 第 2 轮 | A、B、C、D | B→A 没有新属性，停止 |

闭包覆盖 R 的全部属性，所以 AC 是超键。再检查最小性：`A⁺={A,B}`，`C⁺={C,D}`，两者都不能覆盖全部属性，因此 AC 是候选键。

同理，BC 也是候选键。为什么没有漏掉别的候选键？C 从不出现在任何给定依赖的右部，无法由其他属性推出来，所以每个候选键必须包含 C；要得到 A 和 B，至少还要选择 A、B 中的一个。于是全部候选键恰好为 AC、BC。主属性为 A、B、C，非主属性只有 D。

“从不在右部的属性必在每个候选键中”是找起点的技巧，不能替代完整计算。如果所有属性都在右部，仍然可能有候选键，需要继续试探组合。算出超键以后，也必须检验是否能删属性，否则容易把 ABC 这样的非最小超键误写成候选键。

## 先看异常，再理解为什么要规范化

设学校把信息全部放进一张表：

```text
Record(sid, cid, student_name, dept_id, dept_phone, course_name, score)
```

业务规则为：

```text
sid → student_name, dept_id
dept_id → dept_phone
cid → course_name
sid, cid → score
```

假设一名学生只属于一个院系、一门课只有一个课程名称，同一学生同一门课只记录一次成绩。sid 和 cid 都不能从其他属性推出，且 `(sid,cid)⁺` 覆盖全部属性，所以候选键为 `(sid,cid)`。

安禾选了三门课，就会重复三次姓名、院系与院系电话。由此可能出现三种异常：

1. **更新异常**：院系换电话，必须改多行；漏改一行就出现两个不同电话。
2. **插入异常**：新建院系还没有学生、学生尚未选课时，难以在这张以选课为核心的表中独立保存它们。
3. **删除异常**：删除某门课程最后一条选课记录时，可能连课程名称这一独立事实也一起丢失。

根源是“一条选课事实”和“一个学生事实”“一门课程事实”“一个院系事实”混在同一张表中。规范化按依赖分开这些事实，减少特定类型的冗余。它并不承诺任何查询都会更快。

## 1NF 与 2NF：先消除重复组，再消除部分依赖

**1NF** 要求属性的域按当前模型视为不可再分的原子单位。若一格课程写成“C01、C02、C03”，而应用还要逐门选课、逐门记录成绩，就应拆成独立的选课行。不是把所有中文字符串都拆成单个汉字；原子性与这个域如何被使用有关。

Record 每格都只存一个学号、一个课号、一个成绩，可以满足 1NF。但这不代表设计已经合理，因为姓名和院系并不依赖整个复合键。

**2NF** 要求先满足 1NF，且每个非主属性都完全函数依赖于每一个候选键。Record 中：

- `sid → student_name, dept_id, dept_phone`，只用了复合键的一部分。
- `cid → course_name`，也只用了复合键的一部分。
- `sid,cid → score` 才与整条选课事实对应。

可以先拆成：

```text
Student(sid, student_name, dept_id, dept_phone)
Course(cid, course_name)
Enrollment(sid, cid, score)
```

在题设依赖下，这一步消除了选课复合键对姓名、课程名称等非主属性的部分依赖。注意要检查**全部候选键**；“我挑选的主键只有一列”不能一般性地代替 2NF 的定义。

## 3NF 与 BCNF：看决定因素是否足够强

Student 还存着 `sid → dept_id → dept_phone`。院系电话实际由院系决定，同一院系的学生仍然重复保存电话。继续拆分：

```text
Student(sid, student_name, dept_id)
Department(dept_id, dept_phone)
```

于是学生改名只改学生，院系换电话只改院系，选课和成绩单独维护。这个过程把异常与依赖对应起来，而不只是背“3NF 消除传递依赖”。

更精确的判定方法是：先把依赖右部拆成单属性。对每个非平凡依赖 `X → A`，也就是 A 不属于 X：

| 范式 | 要满足的条件 |
| --- | --- |
| 3NF | X 是超键，或者 A 是主属性 |
| BCNF | X 必须是超键 |

定义考虑 F 及其可推导依赖；实际计算可利用等价依赖集与闭包判断。[关系设计作者课件](https://www.db-book.com/slides-dir/PDF-dir/ch7.pdf)给出了正式的 3NF、BCNF 与分解条件。

为什么 3NF 不能只背成“没有传递依赖”？考虑维修分工表 `Assign(station, device_type, technician)`，规则为：某站点某类设备由一位技师负责；每位技师只负责一种设备类型。即：

```text
station, device_type → technician
technician → device_type
```

候选键有 `(station,device_type)` 与 `(station,technician)`，三个属性都是主属性。第二条依赖中 technician 不能推出 station，不是超键；但右部 device_type 是主属性。因此该模式满足 3NF，却不满足 BCNF。**BCNF 比 3NF 更严格，反过来不成立。**

## 分解时必须分开检查两件事

**无损连接**关心信息能否准确还原。把原关系投影到几个子关系，再连接起来，应刚好得到原来的关系，不能额外拼出从未存在的元组。所谓“有损”经常表现为出现伪元组，并非只是丢掉了某一列。

在只有函数依赖、分解为两个关系 R1、R2 的常见题型中，可检查公共属性 `R1∩R2` 能否函数决定 R1 或 R2 的全部属性。能决定其中一边，就满足这一二元无损分解条件。

**依赖保持**关心原来的约束能否仅靠各子关系上的依赖检查出来，而不必先做连接。它和无损连接不是同一个性质。

例如 `R(A,B,C)`，F 为 `A→B, B→C`：

1. 拆成 AB、BC，公共属性 B 能决定 BC，因此无损；A→B、B→C 也都能在单个子关系中检查，因此依赖保持。
2. 拆成 AB、AC，公共属性 A 能决定 AB，因此仍然无损；但 B→C 无法仅由两张表各自的依赖检查出来，因此不保持全部原依赖。
3. 看一个反例：AB 中有 `(a1,b1),(a2,b1)`，AC 中有 `(a1,c1),(a2,c2)`。两张表各自都满足 A 决定另一列，但连接后，同一个 b1 对应了不同的 C，违反 B→C。

同样，前面的维修分工表若按 technician→device_type 拆成 `TechType(technician,device_type)` 和 `StationTech(station,technician)`，可以做到无损并进入 BCNF，却可能失去对“同站同类设备只有一位技师”的局部检查能力。设计时需要权衡，不能认为拆得越细、范式越高就自动解决所有约束问题。[Berkeley 数据库设计讲义](https://cs186berkeley.net/notes/note13/)可用于继续练习依赖和分解。

## 关系代数：把表的运算读成动作

关系代数用关系作为输入与输出。先掌握动作比死记符号更稳：

| 运算 | 动作 | 例子 |
| --- | --- | --- |
| 选择 σ | 按条件筛行 | 从学生中留下 dept_id=D10 的行 |
| 投影 π | 保留指定属性，按集合语义去重 | 只保留学生所属院系 |
| 笛卡尔积 × | 两边所有行两两配对 | m 行与 n 行产生 m×n 个组合 |
| 连接 ⋈ | 保留满足连接条件的组合 | 让选课学号与学生学号相等 |
| 并、交、差 | 合并、取共同部分、排除 | 要先满足并相容的结构要求 |
| 除法 ÷ | 寻找覆盖全部要求的对象 | 选完所有指定课程的学生 |

设选课对为 `(S1,C1),(S1,C2),(S2,C1)`，要求课程为 C1、C2。S1 对应两门要求课，S2 缺 C2，因此“完成所有要求”的结果只有 S1。这里问的是“所有”，不能用“选过其中任意一门”来替代。第 12 章会用双重 `NOT EXISTS` 表达这类查询。

## 做题步骤与自查

范式题按固定顺序做：**列属性和依赖 → 算闭包 → 找全候选键并验证最小性 → 标主属性 → 检查违反范式的依赖 → 验证分解性质**。不要在候选键没找全时就匆忙判断 3NF。

可以自查以下问题：

1. 某集合闭包覆盖全部属性，能直接说它是候选键吗？**只能先说是超键，还要检查最小性。**
2. 右部是主属性的非平凡依赖，左部不是超键，一定不满足 3NF 吗？**不一定；它可能满足 3NF 但违反 BCNF。**
3. 分解无损，就一定依赖保持吗？**不一定，AB、AC 的例子已给出反例。**
4. 当前样本没有重名，就能认定姓名是候选键吗？**不能；要依据业务约束，而不是样本巧合。**
