## 从“测试通过”到“用户可以正常使用”

报修系统在测试环境通过，学校明天能直接使用吗？还要确认服务器配置、真实身份接口、数据库迁移、通知额度、账号权限、用户说明、监控和故障处理安排。**交付**把软件及必要资料交到使用或运行方手中，**部署**把特定版本安装、配置到环境中，**发布**通常指让目标用户获得某项版本或能力。团队对词语可能有不同约定，关键是区分实际动作。

部署和向用户开放可以分开。例如新代码已部署，但新增报修入口由功能开关控制，先只对试点楼栋开放。反过来，切换配置也可能改变用户行为，即使没有重新编译程序。因此版本管理不能只盯着代码文件。

一次交付应能回答：交付了什么版本？怎样安装和配置？怎样知道它工作正常？出问题由谁处理？怎样恢复？业务数据怎样迁移？这些问题的答案应能被别人照着执行，而不是只存在于原开发者脑中。

## 完整例子：一次报修系统发布要检查哪些关系

假设旧版只有“待接单、已完成”，新版加入“处理中”，并增加现场维修照片。软件包可以安装成功，业务仍可能因数据库字段缺失、旧客户端无法识别新状态或照片存储无权限而失败。

可以按一条可追踪链检查：

1. **确定版本组合**：记录代码、依赖、软件包、配置和数据库迁移的对应关系；核对发布说明及已知限制。
2. **准备数据与环境**：演练迁移，确认备份能够恢复，验证外部接口、存储及账号；提前说明停机或使用影响。
3. **部署与有限开放**：先对内部或少量真实流量验证，观察新旧版本协作，而不是仅看进程启动。
4. **检查业务结果**：用约定检查确认能登录、提交、接单、上传照片和查询，并观察错误率及响应时间。
5. **按条件扩大或恢复**：达到观察条件再扩大；若触发失败阈值，停止扩大、隔离新能力或执行恢复方案。

这条链体现“服务可用”比“软件包解压成功”多出的内容。上线检查也不能替代上线前测试，它补充了真实配置、依赖和运行环境中的证据。

## 四类维护：看修改的主要动机

维护是软件交付后的修改及相关活动，往往仍包含分析、设计、编码与测试。常见四类维护按动机区分，不能只看改了哪个文件。

**纠错性维护**修复已经发现的缺陷。例如学生能越权查询他人工单，或撤销后统计仍计为有效工单。关键是原有行为不符合应有要求，修正后恢复正确行为。

**适应性维护**使软件适应变化的环境。例如学校更换身份认证接口、操作系统版本升级、短信接口停用旧格式。变化主要来自外部环境，原程序未必在旧环境里有错误。

**完善性维护**改善能力、性能或使用效果。例如增加按楼栋统计、让管理人员批量导出，或按已确认目标改善查询性能。它关注更好满足持续发展的使用需要。

**预防性维护**着眼于未来的可靠性或可维护性，提前减少潜在故障和修改困难。例如在尚未造成线上故障前替换易出错的重复逻辑、清理难以维护的结构，配合测试证明行为未被破坏。

| 同样是“升级一个库” | 主要原因 | 较合适的分类 |
| --- | --- | --- |
| 修复当前已知错误 | 纠正已有缺陷 | 纠错性 |
| 旧库无法在新运行环境使用 | 适应环境变化 | 适应性 |
| 利用新能力提高用户体验 | 改善现有能力 | 完善性 |
| 在问题显现前降低未来风险 | 预防潜在问题 | 预防性 |

真实修改可能兼有多种动机，分类练习应抓住题干强调的主要目的。“性能优化一定属于某一类”也要看背景：修复不符合既定性能要求的缺陷，与满足新增更高性能目标，不是同一动机。

## CI、持续交付、持续部署：自动化走到了哪一步

**持续集成（CI）**强调经常整合修改，并自动构建和检查。它回答“这批修改与已有系统能否一起工作”。若代码长期在各分支分离，最后集中合并，即使当天启动了测试脚本，也没有充分发挥持续集成的作用。

**持续交付（continuous delivery）**把构建、测试、打包、环境部署等流程做到可靠且可重复，使符合条件的修改保持可发布状态；是否进入生产通常仍可有人工业务决定。**持续部署（continuous deployment）**进一步把符合流水线条件的修改自动部署或发布到生产。实际团队对发布与部署用词应另行约定，但二者的重要辨析是生产步骤是否自动发生。

例如报修项目的流程是“提交→构建→测试→保存产物→部署预发布环境→人工决定生产发布”。这支持持续交付，不等于每次修改都自动进入生产。如果生产步骤也自动执行，则进入持续部署范畴。持续部署同样可以包含自动质量门槛、有限放量和自动停止，不能理解成未经检查就上线。

流水线是按顺序和依赖组织的一组自动化工作。它减少重复手工操作，并保存过程证据；但自动化只是照着规则执行。如果测试没有检查权限，流水线全绿并不能证明权限正确。关键配置与凭据也应受到适当控制，避免把运行秘密写入公开产物或日志。

## 发布策略：怎样控制变更影响范围

**一次切换**把目标范围直接换到新版，安排简单，但失败时可能影响全部用户。**滚动发布**逐批替换实例，让新旧版本在一段时间内共同存在；它通常减少一次替换范围，同时要求接口和数据在混合版本期间兼容。

**蓝绿发布**准备两套可接管服务的环境，先在非当前环境部署验证，再切换流量。若条件允许，可以较快切回旧环境，但要承担额外资源与环境一致性成本；数据库等共享状态的变更不会因为“切回流量”自动恢复。

**灰度或金丝雀发布**先让一部分用户或流量使用新版，观察后逐步扩大。两个词在实践中的使用范围可能重叠，不必脱离题目强行划出绝对边界。金丝雀的重点是用有限范围的真实证据决定继续、停止还是恢复。

例如只向一个楼栋开放新版接单，按相同规则比较成功率、延迟及异常。样本太少、观察时间太短、试点恰好不包含照片上传，都可能使问题暂未暴露。少量流量没有告警，并不等于全量一定安全；选择指标和样本必须覆盖新功能的实际风险。

## 可回滚需要事先设计，代码退回不等于数据退回

**回滚**通常表示恢复到之前已知可用的版本或配置。要做到这一点，需要保留可用旧产物、版本化配置、清楚的切换步骤，以及能判断是否应恢复的指标。恢复方案应经过演练，否则“出现问题再回滚”只是愿望。

最容易被忽略的是数据。新版删除了旧字段并改变数据含义后，旧程序可能无法工作；把旧代码装回去不一定恢复服务。如果直接用昨天备份覆盖数据库，今天已成功提交的工单也可能丢失。因此，回滚、备份恢复与业务数据补偿是不同操作，各有影响。

一种便于理解的兼容式迁移是“先扩展，再收缩”：先增加新字段并让旧版仍可运行；让新版逐步写入并校验新数据；确认所有使用方已迁移后，最后再考虑删除旧字段。每一步仍需结合实际并发、数据量和系统约束设计，不能把这四个字当成自动安全保证。

对于已经发生的外部副作用，如短信已经发出、费用已经扣除，代码回退不会撤回现实结果，可能需要业务补偿或人工处理。有时继续部署一个小修复比机械回到旧版更合理，决定依据应是恢复服务与数据正确性的具体条件。

## 监控：区分实际指标、目标与服务协议

**SLI（服务水平指标）**是对服务表现的量化测量，**SLO（服务水平目标）**给指标规定目标，**SLA（服务水平协议）**通常还约定向服务对象承诺的水平及未满足时的处理。它们不能直接互换。

报修系统可以自行定义：某时间窗内“成功完成有效提交的请求数÷有效提交请求总数”为一个 SLI；“该比例至少达到 99.9%”为一个示例 SLO。若按同一请求口径共有 100000 次有效请求，99.9% 目标对应至多 100 次不成功请求的空间。这个计算以请求为分母，不能直接当成每月停机分钟数。

还可以测量用户实际完成提交的延迟、通知送达情况、积压工单及关键依赖状态。CPU 很低只说明一个资源指标，服务仍可能因为身份接口失败而无法登录。指标必须与用户关心的行为相联系，告警也应能触发明确处理。

## 故障发生后：先恢复服务，再查明原因

假设发布后提交失败率升高。首先确认影响范围与时间，暂停继续扩大，按方案隔离新能力、切回流量或采取其他恢复措施，并持续检查是否确实恢复。只看到某台服务器重启成功，不能马上宣布业务恢复。

服务稳定后，再收集版本、日志、指标及操作记录，查明触发原因和扩大影响的条件，形成改进措施。例如根因可能是新字段未迁移，而检测缺口是预发布环境与生产数据库版本不一致。仅写“提醒大家下次注意”难以验证改进是否生效；增加可检查的迁移门槛和环境检查更具体。

维护工作也应更新需求、设计、测试和说明。若系统行为改了，操作手册仍指导旧流程，就留下新的交付缺陷。用户反馈、监控、问题修复和后续版本应形成持续循环。

## 解题方法、版本号与自查

维护分类先找动机；CI/CD 辨析看自动化到生产的哪一步；发布策略看替换范围和恢复条件；监控题先区分测量、目标和协议。题干写“部署成功但用户不能报修”，应检查业务链路与依赖，不能把部署日志当成最终业务证据。

若明确采用语义化版本并已稳定定义公共 API，`主版本.次版本.修订号` 通常分别表达不兼容 API 变化、向后兼容能力增加、向后兼容问题修正。例如 `1.4.2` 的兼容缺陷修复可成为 `1.4.3`，兼容新增可成为 `1.5.0`，不兼容 API 变化可成为 `2.0.0`。并非所有软件都采用这一约定，版本号大也不自动表示质量好。

自查三个问题：为什么上线前要演练恢复？因为步骤、旧产物和数据条件都可能有误。为什么蓝绿切回仍可能失败？因为共享状态或外部副作用不随流量恢复。为什么监控提交成功率比只看服务器启动更接近使用体验？因为它直接观察用户要完成的任务。
