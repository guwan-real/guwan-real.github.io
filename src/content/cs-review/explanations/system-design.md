## 先建立一条主线

系统设计要回答：**需求已经说明要做什么，接下来怎样组织软件，才能把它做出来，而且以后好修改？**

本节一直用一个自编的“设备报修系统”作例子：报修人填写设备和故障说明；系统建立工单；班组派人；处理完成后关闭工单。它只是帮助理解的教学模型，无须先懂电力业务。

同一套系统可以从不同角度画图：看有哪些类，画类图；看一次提交中谁先调用谁，画时序图；看报修单经过哪些状态，画状态图。**图不是同一信息的不同装饰，而是在回答不同问题。**

建议先读“概要与详细设计”“内聚与耦合”，再看 UML 总览。第一次看图时，先认图形，再按图下步骤读，最后做关联练习；暂时不必背下 UML 的全部图种。

## 概要设计与详细设计

### 需求、设计、编码分别在解决什么

“报修人可以查询自己的工单”是**功能需求**；“查询应在规定时间内返回、普通用户不能看他人的工单”是**非功能或约束需求**。需求分析主要把问题说清楚。

设计进一步决定：划分报修、派工、通知等模块；报修模块提供哪些接口；数据如何保存；如何鉴权；某个函数遇到异常怎样返回。编码再把这些决定变成具体程序。实际项目会来回修订，这种区分是为了识别工作重点，不表示阶段之间永远不能反馈。

| 层次 | 主要问题 | 报修系统中的例子 | 常见成果 |
| --- | --- | --- | --- |
| 概要设计 / 架构设计 | 系统由哪些部分组成，如何协作 | 表现层调用工单服务；工单服务经存储接口访问数据 | 架构图、模块职责、主要接口、总体数据设计 |
| 详细设计 | 每部分内部怎样完成任务 | `assign()` 如何检查状态、选择班组、处理失败 | 类与方法、算法、数据结构、伪代码、详细接口说明 |
| 编码实现 | 用什么语句把设计实现出来 | 写出状态检查、数据库调用、错误处理 | 源代码、构建与单元测试 |

**判断方法**：题目问“整个系统怎么分块”，先想到概要设计；问“这个模块内部算法怎样实现”，先想到详细设计。接口在两层都可能出现，不能看到“接口”二字就一律判概要设计，要看描述的粒度。

### 抽象、逐步求精、信息隐藏

**抽象**是先抓住当前需要的特征。例如调用 `saveTicket(ticket)` 时，只关心能否保存成功，不先讨论磁盘文件具体怎样排列。抽象不是不处理细节，而是把细节留在合适的层次处理。

**逐步求精**是从粗到细展开：受理报修 → 检查设备、校验描述、生成工单 → 再细化“设备不存在时返回什么”。每展开一层，都让下一步更明确。

**信息隐藏**是把容易变化的实现放到模块内部，只暴露必要操作。例如外部调用“保存工单”接口，不直接修改存储模块内部数组。以后从数组换成数据库，调用方就有机会少改。

**封装**是把数据和操作组织在边界内的机制；信息隐藏强调要隐藏什么。声明私有字段有助于封装，但如果接口把所有内部细节都暴露出去，仍然没有很好地实现信息隐藏。

## 模块化：高内聚、低耦合到底是什么

**内聚看模块内部**：放在一起的内容，是否围绕一件清楚的事情？**耦合看模块之间**：一个模块依赖另一个模块有多深，后者改动会牵连多少地方？

把“计算工单费用”单独放进计费模块，里面的操作都服务于同一任务，通常内聚较高。若一个“工具模块”同时处理天气、登录、派工和字体，只因写起来方便就放在一起，内聚通常较低。

低耦合不等于零联系。模块仍需要交换必要信息；目标是用清楚、稳定的接口联系，减少对彼此内部实现的依赖。模块拆得越小也不一定越好：过细会增加接口、调用和理解成本。

### 内聚类型：按“为什么放在一起”识别

下面按传统结构化设计常用的七类口径，由弱到强学习。不同资料还可能单列信息内聚，答题时结合题目给的分类。

| 类型 | 放在一起的理由 | 自编例子 |
| --- | --- | --- |
| 偶然内聚 | 几乎没有业务联系 | 随手把打印、登录、日期换算写在一个函数里 |
| 逻辑内聚 | 都属某一类，由参数选做哪一个 | `handleInput(kind)` 按 kind 选择键盘、文件或网络输入 |
| 时间内聚 | 恰好同一时间执行 | 启动函数里开日志、读配置、连打印机 |
| 过程内聚 | 只因要求按某个步骤顺序执行 | 一个例程先更新界面，再检查权限，两者不传递同一处理数据 |
| 通信内聚 | 操作围绕同一组输入或输出数据 | 对同一工单分别生成摘要和联系人列表 |
| 顺序内聚 | 前一步输出是后一步输入 | 读取故障文本 → 清洗文本 → 生成清洗后摘要 |
| 功能内聚 | 全部内容共同完成单一明确功能 | 校验一张报修单是否合法，所有检查都服务这一目标 |

“先做 A 再做 B”本身不能证明顺序内聚；要找 **A 的输出是否成了 B 的输入**。“都属于输入处理”也不一定是功能内聚，若由标志选择互不相同的处理，可能是逻辑内聚。

### 耦合类型：按“传了什么、依赖到哪里”识别

| 类型 | 具体依赖 | 例子与问题 |
| --- | --- | --- |
| 数据耦合 | 通过参数传必要的数据值 | `calculateFee(hours, rate)`，只传需要的工时和费率 |
| 标记 / 印记耦合 | 传整个结构，实际只需其中一部分 | 计费只要工时，却传入包含地址、电话的完整工单对象 |
| 控制耦合 | 传标志来控制另一个模块的内部分支 | `process(ticket, mode)` 中 mode 指定“保存/打印/删除” |
| 公共耦合 | 多个模块共享并修改公共数据 | 都能任意改全局工单列表，难以追踪是谁改坏 |
| 外部耦合 | 共同依赖外部规定的协议、格式或设备接口 | 两模块都依赖某设备规定的报文格式 |
| 内容耦合 | 直接使用或修改另一个模块内部内容 | 绕过接口改别的模块私有数据，或跳入其内部代码 |

传统题通常把数据耦合视为较松、内容耦合视为最紧的一端；不同教材对中间类型的排列可能不同，**先用定义判断，不能只背一条绝对排序**。传递一个正常业务对象不必然就是不合理的标记耦合，关键在它是否暴露了不必要的结构依赖。

**小例题**：A 只为获得工单编号，却直接读取 B 的内部数组下标。问题不是“调用次数多”，而是依赖了 B 的内部表示。改成 `getTicketId()`，才能把这种依赖移到公开边界。

## 常见架构：先看组织方式

**架构风格**描述整个系统怎样组织；**设计模式**通常描述某类对象协作问题的可复用办法。二者处于不同粒度。

| 组织方式 | 核心结构 | 容易理解的例子 | 需要留意 |
| --- | --- | --- | --- |
| 分层 | 各层承担不同职责，按约定访问其他层 | 页面层 → 工单业务层 → 数据访问层 | 严格分层限制跨层；逻辑层不等于独立机器 |
| 客户端 / 服务器 | 客户端提出请求，服务端提供服务 | 浏览器查询工单，服务端返回结果 | 不是所有程序都必须拆成两个部署部分 |
| 仓库 / 共享数据 | 多个处理部件围绕共享数据工作 | 多个分析工具访问共同工程数据 | 中心数据结构变化可能影响多个部件 |
| 管道—过滤器 | 数据流经一系列变换，每步输出交给下步 | 采集日志 → 清洗 → 聚合 → 报告 | 适合阶段性数据变换；交互密集任务未必适合 |
| 事件驱动 | 发生事件后，由感兴趣的处理器响应 | 工单已关闭 → 发送通知、更新统计 | 需处理事件顺序、重复与失败 |
| MVC | Model 管数据与业务，View 展示，Controller 接收并协调输入 | 用户点查询，控制器取模型数据交给视图 | MVC 不是简单给三层换名字 |

**三层架构和三台服务器不同**：三层可以在同一个进程中；也可以把某一层部署成多台机器。“怎么分职责”属于逻辑设计，“跑在哪里”属于部署设计。

## UML 总览：一道题该选哪张图

UML 是**统一建模语言**，用一套约定的符号表达模型。它不是 Java 一样的编程语言，也不是固定的开发流程；画了 UML 不代表程序会自动正确。

**结构图**主要描述“有什么、怎样连接”；**行为图**主要描述“会做什么、怎样变化”。时序图属于行为图中的交互图。注意“描述静态结构”不表示系统数据永远不变化。

| 图 | 最想回答的问题 | 识别外形 |
| --- | --- | --- |
| 类图 | 有哪些类、属性、操作及关系？ | 分栏矩形、关联线、三角形和菱形 |
| 对象图 | 某一时刻有哪些具体对象及连接？ | 具体对象名与属性值，是实例快照 |
| 用例图 | 哪种外部角色，能通过系统达成什么目标？ | 小人、椭圆、系统边界框 |
| 时序图 / 顺序图 | 一次交互中，谁按什么先后发消息？ | 顶部参与者、竖直生命线、横向消息 |
| 通信图 | 哪些参与者相互联系、消息次序是什么？ | 对象连接网络和带编号的消息 |
| 活动图 | 一项业务流程怎样分支、并行、结束？ | 圆角动作、菱形、粗横条 |
| 状态机图 / 状态图 | 一个对象遇到事件后怎样换状态？ | 状态、带事件条件的迁移箭头 |
| 组件图 | 软件组件通过什么接口依赖？ | 组件矩形、接口和依赖线 |
| 部署图 | 软件制品部署到哪些运行节点？ | 节点立方体、内部制品、节点间连接 |

包图用于组织模型元素；组合结构图展开分类器内部结构；轮廓图用于扩展建模约定；交互概览图组织交互流程；定时图强调随时间变化及时间约束。初学先掌握上表的用途，再识别其余名称。

## 类图：矩形里的三栏怎么读

[![工单类的三栏，以及工单与设备的一对多关联示意。](/appendix/cs-review/figures/system-design-class.svg)](/appendix/cs-review/figures/system-design-class.svg)

先看左边的“工单 Ticket”。上栏是**类名**；中栏是**属性**，也就是对象保存的资料；下栏是**操作**，也就是它提供的行为。省略属性栏或操作栏不表示这个类一定没有属性或操作，可能只是当前图省略了细节。

`-status: Status` 表示名为 status、类型为 Status 的私有属性。`+assign(worker: Worker): void` 表示公开操作 assign，接收 Worker 类型参数，不返回业务值。常用可见性符号是 `+` public、`-` private、`#` protected、`~` package；带下划线的特征通常表示分类器级（如静态成员），斜体名称常用于表示抽象。

### 多重性要读“对面有几个”

图中设备端写 `1`，工单端写 `0..*`。读法是：**每张工单对应 1 台设备；对 1 台设备，可以有 0 到多张工单。** 两端的数不是当前数据库已有几条记录，而是模型允许的数量约束。

| 符号 | 含义 |
| --- | --- |
| `1` | 恰好一个 |
| `0..1` | 可以没有，最多一个 |
| `*` 或 `0..*` | 零到任意多个 |
| `1..*` | 至少一个 |
| `2..5` | 至少两个，至多五个 |

做题时把手指按在一端，问“固定这一个对象，另一端允许几个”，就不容易把多重性读反。

### 类与对象不要混

Ticket 是“工单这一类东西”的定义，`ticket42: Ticket` 是具体的一张工单。类图可以规定所有工单都有状态字段；对象图则可展示 ticket42 当前状态为“已派工”。**类是类型，对象是实例。**

## 类之间的六种关系

[![六种 UML 类关系，分别示出实线、虚线、空心三角形、空心菱形和实心菱形的放置位置。](/appendix/cs-review/figures/system-design-relations.svg)](/appendix/cs-review/figures/system-design-relations.svg)

### 关联与依赖：认识你，还是临时用你

**关联**表示实例之间存在某种结构联系，用实线。例如工单与设备关联；建模时常可由持有引用的字段实现。需要表达可导航方向时可以加开放箭头；未画导航箭头时，不要擅自认为“程序必然双向持有引用”。

**依赖**表示一个元素的定义或实现用到了另一个元素，常画虚线加开放箭头，指向被依赖者。例如报修服务在某个操作中调用通知接口。参数或局部变量是常见线索，但不是定义本身；同一对类也可能同时存在不同层次关系。

### 泛化与实现：三角形都朝抽象的一端

**泛化**表达“是一种”：紧急工单是一种工单。画**实线加空心三角形**，从具体子类指向一般父类。继承应满足合理的替换关系，不能只因为两个类碰巧有相同字段就强行继承。

**实现**表达“满足某份契约”：短信通知器实现通知接口。常画**虚线加空心三角形**，指向接口或规范。它与泛化的主要识图差别是实线 / 虚线，不能把所有三角形都读成继承。

### 聚合与组合：菱形在整体一端

**共享聚合**用空心菱形，表示较弱的整体—部分语义。例如把班组与员工建模为聚合，员工仍可独立存在。UML 对共享聚合的精确语义留给具体模型说明，不能由空心菱形推出统一的数据库删除规则。

**组合**用实心菱形，表示较强的整体—部分与生命周期约束。例如教学模型规定“工单明细项由工单独占拥有”：一个部分在同一时刻最多属于一个组合整体；整体删除时，仍属于它的部分也随之删除。部分如果在整体删除前已被移出，则不能机械推出仍被删除。

**读图三问**：先看实线还是虚线；再看三角形还是菱形；最后看符号放在哪端。三角形指向较抽象一端，菱形贴着整体一端。

## 用例图：外部角色用系统做什么

[![报修人在系统边界之外，提交报修单包含校验表单，附加现场照片可扩展提交报修单。](/appendix/cs-review/figures/system-design-use-case.svg)](/appendix/cs-review/figures/system-design-use-case.svg)

**参与者 Actor**是系统之外与其交互的角色，可以是人，也可以是其他系统。“报修人”是角色，不是特指某一个人的账号；同一个人可以扮演多个角色。系统边界框说明我们当前讨论的是哪个系统，参与者画在边界外。

**用例**用椭圆表示可为参与者带来价值的目标，如提交报修单、查询进度。用例图侧重目标与关系，不能把它当成按从左到右顺序执行的流程图；详细场景还应写前置条件、基本流程、备选流程和后置条件。

### include 与 extend 的方向

图中“提交报修单”虚线指向“校验表单”，标 `«include»`：前者的行为中纳入后者所描述的行为。它用于抽出可复用的子行为；“必需的公共子过程”是常见考试情境，但不要把它误解为界面上必须点击一个独立按钮。

“附加现场照片”虚线指向“提交报修单”，标 `«extend»`：在指定扩展点、满足条件时，为基础用例补充行为。基础用例本身应能独立有意义。此例没照片也能提交，用户选择附图时才补充。

记箭头可以说完整句子：**基础用例 include 被包含用例；扩展用例 extend 基础用例。** 它们都画虚线开放箭头；参与者之间或用例之间也可能有泛化，用空心三角形，别混在一起。

## 时序图：一次请求到底怎样发生

[![报修人、报修页面、工单服务三条生命线，包含同步调用、返回消息，以及设备有效和无效两种 alt 分支。](/appendix/cs-review/figures/system-design-sequence.svg)](/appendix/cs-review/figures/system-design-sequence.svg)

### 先认四种东西

1. **参与者头部**：上方的报修人、页面、工单服务，代表参与这次交互的角色或实例。左右位置主要用来排版，不表示执行先后。
2. **生命线**：头部往下的竖直虚线，用来安排该参与者的事件。通常沿同一生命线从上往下读先后；图上两个事件相隔多远，一般不代表过了几秒。
3. **消息**：横向箭头表达发出与接收。同步调用通常是实线加实心箭头；异步调用通常是实线加开放箭头；返回消息常用虚线加开放箭头。返回线可以省略，省略不等于没有返回。
4. **执行条 / 激活条**：生命线上的细长矩形，表示执行某项行为的区间。它不是 CPU 占用率，也不意味着对象只在这段时间存在。

### 按图一步步读

**第一步**，报修人把提交请求发给页面。页面开始处理输入。**第二步**，页面向工单服务发 `create(deviceId, description)`，把必要数据交过去；服务开始执行。

**第三步**，进入 `alt` 组合片段，上半段守卫条件是 `[设备有效]`：服务建立工单，返回工单编号；页面再向报修人显示受理结果。

**第四步**，下半段 `[else]` 是另一种情形：不建立有效工单，服务返回错误，页面提示修改。两段表示备选行为，**不是先成功一遍，再失败一遍**。这个例子把守卫条件写成互斥且覆盖两种情况，避免多条件同时成立的歧义。

如果把“发邮件通知”画成异步消息，发出者通常不需要阻塞等待这条消息完成；但异步不表示系统保证立即送达，也不表示永远不会处理失败。

### 常见组合片段

| 标记 | 类比 | 怎么读 |
| --- | --- | --- |
| `alt` | if / else | 满足守卫条件时选择可用分支，常用互斥条件建模 |
| `opt` | 只有 if，没有 else | 条件满足才执行该片段，否则跳过 |
| `loop` | 循环 | 按次数范围、条件重复片段，次数条件要看标注 |
| `par` | 并行 | 不同操作数中的行为可交错；各自内部仍受其顺序约束 |

时序图强调的是事件先后及消息交互，不自动给出全局严格的时间顺序：不同生命线上无约束的事件未必能仅凭画得高低就确定先后。题目若给 `par` 或明确时间约束，更要看约束本身。

**时序图与定时图**：若重点问“谁先调用谁”，通常是时序图；若重点是值或状态在明确时间轴上的变化、持续时间限制，则要想到定时图。中文“时序”一词可能有不同用法，结合题图判断。

## 活动图与状态图：流程和对象状态要分开

### 活动图：一件事怎样做下去

[![受理报修的活动流程：提交与校验、完整性判断、创建工单、并行记录审计与发送通知，汇合后显示编号。](/appendix/cs-review/figures/system-design-activity.svg)](/appendix/cs-review/figures/system-design-activity.svg)

活动图里的圆角框常表示**动作**，例如“校验信息”。黑色实心圆是初始节点；靶心状圆是活动终结节点。箭头说明控制或数据如何流动，不能看到箭头就以为它一定表示函数调用。

菱形可以表示**决策**或**合并**：决策按边上的 `[完整]`、`[不完整]` 选择后继；合并把备选路径汇回，不负责等待所有分支。粗横条可以表示**分叉 fork**或**汇合 join**：图中创建工单后，记录审计和发送通知可并行，下面的 join 在本例默认语义下等待两个分支都完成，再显示编号。

**关键辨析**：决策是“选哪条路”；分叉是“多条路都开始”。合并不是同步点，join 才用于同步并行流。活动终结结束整个活动；带叉的流终结只结束当前一条流，二者也不同。

泳道用于划分动作由哪个角色或组织负责，不表示物理线程或固定执行时间。没有泳道也不妨碍活动图表达业务流程。

### 状态图：同一张工单现在处于哪里

[![工单从草稿到已提交、已派工、已关闭，或由已提交取消；迁移线上写事件、守卫条件与动作。](/appendix/cs-review/figures/system-design-state.svg)](/appendix/cs-review/figures/system-design-state.svg)

状态是对象在一段时间内满足的条件，如“已提交”“已派工”。箭头叫**迁移**，常见标注格式为：

```text
事件 [守卫条件] / 迁移动作
submit [信息完整] / 生成工单编号
```

读成：对象当前处于草稿状态，**发生 submit 事件，并且信息完整**，才沿箭头迁移到已提交；迁移过程中执行生成编号。方括号内是能否走这条边的条件，不是新状态；斜杠后是迁移动作，不是触发事件。无触发器的完成迁移有特定语义，不等于任意时刻可无条件乱跳。

**按图推演**：草稿 → submit[完整] → 已提交 → assign → 已派工 → complete → 已关闭。如果草稿信息不完整，不能走提交迁移；图中只允许已提交状态取消，所以不能自行补出“已派工也能取消”。缺失需求时应补模型，做题时不能凭生活经验替图添加边。

状态还可定义 `entry / 动作`、`do / 活动`、`exit / 动作`，分别在进入、处于、退出该状态时执行。入门先分清这些动作与迁移线上的动作。

**两图区别**：“校验—创建—通知”问工作步骤，选活动图；“草稿—已提交—已派工”问工单生命周期，选状态图。状态名不必永远是形容词，动作名也不必永远是动词，判断依据是图描述的语义。

## 组件图与部署图：软件怎么连，运行在哪里

[![上半部分为组件依赖：页面组件依赖工单组件，后者依赖存储组件；下半部分为浏览器、应用节点和数据库节点的部署示意。](/appendix/cs-review/figures/system-design-deployment.svg)](/appendix/cs-review/figures/system-design-deployment.svg)

上半部把页面、工单业务、存储看作软件组件，关注提供 / 需要哪些接口以及依赖关系。组件图可以用 `«component»` 矩形表示组件，也可用组件图标；小圆球常表示提供的接口，半圆“插座”常表示需要的接口。

下半部把浏览器所在设备、应用运行环境、数据库运行环境看作节点，展示制品部署的位置与通信连接。节点可以是设备或执行环境，并不只能是一台实体服务器。

**组件不等于文件，节点不等于类**。一个组件可能由多个文件实现；一个节点可以部署多个制品。图中三节点报修系统是教学示例，不表示本学习网站需要增加服务器。

## 设计原则与常见模式：先找变化点

### 五个常见面向对象原则

| 原则 | 白话含义 | 报修系统中的例子 |
| --- | --- | --- |
| 单一职责 SRP | 一类职责的变化有清楚的归属 | 工单计费和短信发送分开，不因短信变更去改计费类 |
| 开闭原则 OCP | 尽量通过扩展应对变化，减少修改稳定代码 | 新增一种计费策略时沿共同接口接入 |
| 里氏替换 LSP | 子类型能遵守父类型约定，被正确替换使用 | 不能用“紧急工单”子类破坏父类承诺的合法操作 |
| 接口隔离 ISP | 调用方不要依赖它不需要的方法 | 只查进度的客户不必依赖管理员删除接口 |
| 依赖倒置 DIP | 高层策略和低层细节面向合适的抽象协作 | 工单服务依赖通知接口，不写死短信厂商类 |

依赖倒置是一项设计原则；依赖注入是把依赖提供给对象的实现方式之一，两者不能直接画等号。原则也不是越抽象越好：只有一种稳定行为时，过多接口反而增加理解成本。

### 工厂、策略、观察者分别解决什么

**工厂相关模式**重点是“由谁、怎样创建对象”。例如根据通知渠道建立相应通知器。简单工厂常用一个集中创建函数；工厂方法由子类等机制决定创建哪类产品；抽象工厂组织一族相关产品的创建。三者不能只因名称都带工厂就混为同一模式。

**策略模式**重点是“同一任务的不同算法可替换”。例如普通工单按工时计费，特殊工单按包干规则计费；调用方只调用共同的 `fee()`。下面是策略思想的最小教学例子，不要求先会 TypeScript：

```ts
type FeeRule = (hours: number) => number;
const hourly: FeeRule = hours => hours * 80;
const fixed: FeeRule = _hours => 200;

function estimate(hours: number, rule: FeeRule) {
  return rule(hours); // 把“选用哪套算法”从计算入口中分离
}
estimate(3, hourly); // 240
estimate(3, fixed);  // 200
```

**观察者模式**重点是“一方变化，通知多个订阅者”。例如工单关闭后，已订阅的统计部件和通知部件各自更新；新增订阅者不必把它的具体业务全部塞进工单对象。需要考虑取消订阅和通知顺序；它本身不保证跨网络可靠投递，也不强制异步。

**辨析题**：题干说“按条件产生不同通知器”，看创建对象，想到工厂；说“运行时换计费算法”，看替换行为，想到策略；说“状态改变后通知多个订阅方”，看一对多通知，想到观察者。

## 把一道设计题拆开做

设题目描述：“设备有多张历史工单；一张工单只对应一台设备。提交后若校验通过则创建工单，否则返回错误。已提交工单可被派工；已派工后才能完工。关闭时通知统计和消息模块。”

1. **抽取名词与数量约束**：设备、工单 → 类图；设备端 `1`，工单端 `0..*`，表示允许设备暂无工单。
2. **抽取交互先后**：页面调用服务，服务返回结果 → 时序图；校验成功与失败可用 `alt` 建模。
3. **抽取生命周期**：已提交、已派工、已关闭 → 状态图；先画允许的边，再代入事件序列判断可达性。
4. **抽取算法或通知变化**：关闭后通知多个订阅者 → 观察者；若只是依次调用两个固定函数，不能仅凭有两个调用就断言已实现观察者。
5. **检查设计边界**：若页面直接修改存储组件私有数据，指出信息隐藏被破坏、依赖过深；给出通过公开接口访问的改法。

答题时不要先背一堆模式名称，再强行套上去。先找题目要表达的是结构、交互、流程还是状态，再判断符号和约束。
